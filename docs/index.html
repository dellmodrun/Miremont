Start with the model.

Miremont turns token destruction into limited build capacity. Burning does not buy passive yield: it creates one attempt to complete one public task.

01. Burn and spawn.

One Cursor costs 0.001% of the mint's current total supply. At one billion tokens, the burn is 10,000 MIREMONT. The interface reads supply at signing time and shows the exact irreversible amount before approval.

burn_unit = ceil(total_supply x 0.00001)

1 successful burn
= 1 wallet-linked Cursor
= 1 active task slot
= 1 Build Receipt account
Atomic rule

All created or nothing created.

The burn, Cursor account and initial receipt must be initialized in one atomic transaction. If account creation fails, the transaction fails as a whole. Once confirmed, the burn cannot be refunded.

02. Cursor lifecycle.

A Cursor is temporary build capacity, not a permanent reward position. It owns one task at a time and reaches exactly one final outcome.

Active

Task leased

Scope, tests, 72-hour deadline, base points and destination are locked.

Submitted

Output committed

The artifact destination and content hash are frozen for verification.

Verifying

Checks + quorum

Required tests run and independent reviewers submit verdicts.

Final

Accepted or rejected

The receipt receives points and an epoch, or closes with zero reward.

Default lease

72 hours

No submission before expiry closes the task as expired. The burn remains permanent.

One-at-a-time

1 active task

A Cursor cannot reserve multiple jobs or accumulate idle reward rights.

Public evidence

Permanent receipt

The lifecycle remains visible even after rejection, expiry or claim.

03. Verification.

A submission must clear deterministic requirements and independent review. Required checks are committed before the burn, so they cannot be changed to favor or block a builder afterward.

100%required tests must pass
2 / 3review approval quorum
24Hchallenge window
0self-review weight
Automatic rejection

Failed hard check

A failed required test, missing artifact, invalid hash, duplicate output or late submission cannot receive a quality score.

Reviewer eligibility

Independent wallets

The builder cannot review their own work. One wallet counts once per receipt and a reviewer must submit before quorum closes.

Dispute path

Evidence, not votes

A challenge identifies a committed rule and verifiable failure. Valid evidence reopens review; unsupported challenges do not delay settlement.

04. Contribution points.

Points measure accepted work inside one reward epoch. They are not transferable tokens, do not compound and do not survive as a permanent claim on future fees.

base_points = 100
difficulty  = 1x | 2x | 4x
quality     = 0.75x | 1.00x | 1.25x

receipt_points = min(
  base_points x difficulty x quality,
  500
)
Examples

Easy 75 · Standard 200 · Maximum 500

An easy task rated adequate earns 75 points. A medium task rated standard earns 200. A hard task rated excellent reaches the 500-point receipt cap. Rejected work always earns zero.

05. Creator-fee rewards.

Only net SOL visibly deposited into the Fee Router is distributable. External platform balances are not advertised as vault funds. Every 24-hour epoch uses a deterministic split.

70%accepted builder pool
15%eligible reviewer pool
10%protocol operations
5%safety reserve
builder_claim = (wallet_points
  / epoch_accepted_points)
  x (epoch_net_sol x 0.70)

reviewer_claim = valid_review_units
  / epoch_review_units
  x (epoch_net_sol x 0.15)
Settlement rules

Daily epochs, wallet-bound claims.

Epochs close at 00:00 UTC. Only finalized receipts participate. Empty builder or reviewer shares remain unallocated and roll forward. Protocol v0.1 does not expire valid claims.

06. Safety and failure rules.

The protocol must remain understandable when things go wrong. These boundaries prevent the interface from promising recovery or rewards the program cannot guarantee.

Transaction failure

No Cursor, no burn

Atomic initialization failure reverts the whole transaction. Network fees may still apply according to Solana behavior.

Task failure

Burn remains final

Expiry, abandonment and rejection produce zero points and no refund. The failed receipt stays public.

Output commitment

One immutable hash per Cursor

A submitted Cursor stores one fixed output commitment. Cross-Cursor duplicate detection is an application-layer verifier responsibility in v0.1.

Operator limits

No claim redirection

A claim is bound to the builder or reviewer wallet recorded on the receipt.

Parameters

Immutable in v0.1

The deployed configuration exposes no parameter-update instruction. A future upgrade policy must be published before mainnet deployment.

Truthful interface

Mainnet TBA means unavailable

The browser exposes working localnet transactions while mainnet actions remain blocked until the official CA and deployment are verifiable.

07. Task and project contracts.

The task market is the protocol entry point. Project authorities publish immutable task contracts; builders inspect them before burning and can trace accepted output into a project release.

Task PDA

Terms before work

Project, scope hash, artifact destination, role, lease, base points, difficulty and acceptance policy.

Project PDA

Shared product state

Authority, artifact root, verifier set, active tasks, accepted receipts and published releases.

Release record

Outcome provenance

Version, included artifact hashes, contributing receipts, deployment transaction and release notes.

08. Public data interfaces.

The commercial interface requires a chain indexer and live event service. The endpoint shapes are specified now; production URLs activate only after deployment and health verification.

Live event envelope

Cursor events remain attributable.

Each message carries program slot, Cursor account, receipt account, event type, UTC time, public payload and transaction signature. Private model reasoning and credentials are never streamed.
