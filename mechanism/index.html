Protocol / Mechanism

Burn creates productive capacity.

Network · SolanaToken CA · TBASettlement · SOL

A Miremont token burn creates one wallet-linked Cursor. That Cursor completes one build task, receives verification and—only when accepted—enters the creator-fee reward cycle.

One transaction starts the build.

The burn, Cursor creation and Build Receipt initialization are designed as one atomic Solana flow. If initialization fails, the transaction does not produce a valid Cursor.

One public burn unit.

Protocol v0.1 fixes one Cursor at 0.001% of the live token supply. At a one-billion-token supply, that is 10,000 MIREMONT. The exact amount is displayed before wallet approval.

Protocol v0.1

0.001% of current supply

One successful burn creates exactly one Cursor and one task attempt. Burns are permanent. Rejected, abandoned and expired tasks receive no refund and no reward.

supply = mint.total_supply
burn_unit = ceil(supply × 0.00001)

burn(builder, burn_unit)
spawn(cursor, task_slot = 1)
record(receipt, status = "active")

The rules are fixed before work begins.

Each task publishes its scope, output destination, deadline, base points and acceptance checks before a wallet burns. The builder sees the complete contract before signing.

Visible task contract

Scope, deadline, base points, checks and required artifact cannot be rewritten after the burn.

At submission

Immutable output hash

At finality

Challenge before settlement

An accepted result waits 24 hours before it can enter the next reward epoch.

Burning is access. Work earns rewards.

A burn alone never earns SOL. The output must satisfy the task’s acceptance rules and receive an accepted Build Receipt.

Gate 01

Deterministic tests

All required checks must pass. A failed required test means rejection, not a lower score.

Gate 02

Independent quorum

Two of three eligible reviewers must approve. A builder cannot review their own receipt.

Gate 03

Final receipt

After the 24-hour challenge window, verdict, output hash, wallet, points and epoch become auditable state.

difficulty = 1x / 2x / 4x
quality = 0.75x / 1.00x / 1.25x
points = min(100 x difficulty
         x quality, 500)
Scoring boundary

75 to 500 points per receipt.

Difficulty is committed before burning. Quality is decided by quorum only after required checks pass. A single receipt can never exceed 500 points.

Minimal program surface.

The protocol is intentionally small: burn, spawn, submit, verify, settle and claim. The public interface below is the implementation target, not a claim of a deployed program.
